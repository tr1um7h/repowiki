## 核心设计理念

### 确定性构建系统

**核心思想**：repowiki 本身不包含 LLM，它是一个确定性的任务编排器。

```
传统方案：
  云端服务（内置 LLM） → 读代码 → 写文档
  ↑ 一体化，不可拆分，质量黑盒

repowiki 方案：
  Agent（可选任意 AI/人） → 读代码 → 写文档
       ↑                          ↓
  确定性框架（repowiki）← 校验规则 + 模板约束
  ↑ 分离，可组合，质量可控
```

**关键原则**：

1. **Agent 负责智能工作**：读代码、理解代码、撰写文档
2. **repowiki 负责确定性工作**：规划任务、校验产出、自动修复、组装元数据
3. **零 LLM 依赖**：repowiki 不依赖任何特定的大模型
4. **Agent 可替换**：可以使用 Claude Code、OpenCode、人工操作或其他任何执行者

### 为什么这样设计？

| 方案 | LLM 选型 | 工具能力 | 反馈修正 | 并发支持 | 质量保证 |
|------|---------|---------|---------|---------|---------|
| 云端服务 | 固定 | 有限 | 无 | 无 | 黑盒 |
| repowiki | 可选 | 丰富 | 多轮 | 安全 | 确定性校验 |

**本质**：
- Agent = "大脑 + 手"（智能 + 执行）
- repowiki = "尺子 + 模板"（框架 + 约束）

4. **并发安全**：原子认领 + 过期回收 + 心跳续期
5. **渐进式**：支持部分完成、断点续跑、增量更新

## 三阶段任务流程

### Phase 1: Catalog（目录规划）

**目标**：规划 Wiki 目录树结构

**输入**：
- 仓库文件清单（scanner 扫描）
- 仓库信息（REPO_NAME、KEY_FILES）
- 文件树摘要

**流程**：

```
┌─────────────────────────────────────────────────────┐
│ 1. Scanner 扫描仓库                                  │
│    - git ls-files 或文件系统遍历                     │
│    - 识别代码文件（按扩展名）                         │
│    - 统计 LOC、识别关键文件                          │
│    - 生成文件树摘要（每目录最多 20 个文件）           │
│    - 代码文件清单（最多 800 个，超出截断）            │
└─────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│ 2. Tasks 生成 catalog 任务规格                       │
│    - 模板: templates/zh/catalog_task.md              │
│    - 注入: 文件清单、仓库信息                         │
│    - 输出: state/tasks/catalog.md                    │
└─────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│ 3. Agent 执行 catalog 任务                           │
│    - Read: state/tasks/catalog.md                    │
│    - LLM: 规划目录树（JSON Schema）                   │
│    - Write: state/catalog.json                       │
└─────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│ 4. repowiki 校验 catalog                             │
│    - JSON Schema 验证                                │
│    - dependent_files 路径验证                        │
│    - title/slug/id 唯一性验证                        │
│    - 树深度验证（≤ 4）                               │
└─────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│ 5. Tasks 展开 page 任务                              │
│    - 从 catalog.json 提取节点                        │
│    - 为每个节点生成 page 任务规格                     │
│    - 输出: state/tasks/{id}.md                       │
└─────────────────────────────────────────────────────┘
```

**Agent 决策**：

在 catalog 任务中，Agent 需要：
1. **理解仓库结构**：根据文件清单、文件树、关键文件
2. **划分章节**：按主题而非机械按目录
3. **选择文件**：每个页面 3~12 个最具代表性的文件
4. **编写 page_brief**：该页面要覆盖的内容要点

**关键约束**：

```json
{
  "repo_name": "<仓库名>",
  "chapters": [
    {
      "id": "c01",
      "title": "<章节标题>",
      "slug": "<english-slug>",
      "summary": "<一句话描述>",
      "kind": "chapter",
      "dependent_files": ["<路径>"],  // 3~12 个
      "page_brief": "<内容要点>",
      "children": [...]
    }
  ]
}
```

### Phase 2: Page（页面撰写）

**目标**：逐页撰写 Wiki 内容

**输入**：
- 任务规格（state/tasks/{id}.md）
- 参考文件（dependent_files）
- 页面模板、文风规范

**流程**：

```
┌─────────────────────────────────────────────────────┐
│ 1. Agent 领取任务                                    │
│    - Bash: repowiki next . --claim --json            │
│    - 返回: tasks[0].instructions                     │
└─────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│ 2. Agent 理解任务                                    │
│    - Read: state/tasks/{id}.md                       │
│    - LLM: 理解要写什么、不能写什么                    │
└─────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│ 3. Agent 读取代码文件                                │
│    - Read: dependent_files[0]                        │
│    - Read: dependent_files[1]                        │
│    - ...                                             │
│    - LLM: 理解每个文件的内容                          │
└─────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│ 4. Agent 理解代码结构                                │
│    - LLM: 分析代码结构                               │
│    - LLM: 提取关键类、函数、流程                      │
│    - LLM: 生成文档大纲                               │
└─────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│ 5. Agent 生成文档                                    │
│    - LLM: 根据代码内容 + 模板 + 规范                 │
│    - 生成: markdown 文本                             │
└─────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│ 6. Agent 写入文件                                    │
│    - Write: .repowiki/zh/content/{path}.md           │
└─────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────┐
│ 7. Agent 校验                                        │
│    - Bash: repowiki check . --task {id}              │
│    - 返回: ok: true/false + errors                   │
└─────────────────────────────────────────────────────┘
                         ↓
          ┌────────────────────────────────┐
          │ ok: true?                      │
          └────────────────────────────────┘
             │                    │
            Yes                   No
             │                    │
             ↓                    ↓
    ┌────────────────┐   ┌─────────────────────┐
    │ 任务完成        │   │ 8. Agent 修复        │
    │                │   │ - Read: 文档         │
    │                │   │ - LLM: 根据 errors   │
    │                │   │ - Write: 修复后内容  │
    │                │   │ - 重新 check         │
    │                │   └─────────────────────┘
    └────────────────┘            ↓
                          （循环直到 ok: true）
```

**Agent 的实际工作**：

一个页面任务的实际执行包含：

```
工具调用次数: 10-15 次
  - Read: 4-7 次（读代码文件）
  - Write: 1-3 次（写文档 + 修复）
  - Bash: 2-3 次（check + retry）

LLM 推理次数: 10-15 次
  - 理解任务规格: 1 次
  - 理解代码文件: 4-7 次
  - 生成文档: 1 次
  - 修复（如有）: 2-3 次

Token 消耗: 约 50k-100k tokens
  - 是单次 LLM 调用的 10-20 倍
```

**校验内容**：

repowiki 的确定性校验：

1. **H1 检查**：必须是任务指定的标题
2. **锚点修复**：自动修正中文锚点格式
3. **行号修复**：自动修正超出范围的行号
4. **路径验证**：验证 file:// 引用的文件是否存在
5. **占位符检查**：扫描未替换的 {{...}}
6. **模板合规**：检查必备小节是否存在

**自动修复**：

确定性缺陷会被自动修复，Agent 只需修复语义问题：

```python
# validate.py
def auto_fix(content, task_spec):
    # 1. H1 修复
    content = fix_h1(content, task_spec["title"])
    
    # 2. 锚点修复
    content = fix_anchors(content)
    
    # 3. 行号修复
    content = fix_line_ranges(content, actual_file_lines)
    
    return content
```

**并发安全机制**：

```python
# state.py
class TaskStore:
    def claim(self, task_id, worker):
        """原子认领"""
        claim_dir = self.claims_dir / f"{task_id}.{worker}"
        
        # 原子操作：mkdir 失败说明已被他人认领
        try:
            claim_dir.mkdir(parents=True, exist_ok=False)
            # 更新任务状态
            self._update_task(task_id, {
                "status": "in_progress",
                "worker": worker
            })
            return task
        except FileExistsError:
            raise ConflictError(f"任务 {task_id} 已被他人认领")
```

## 文件选择机制

### 核心问题

一个目录下有 35 个文件，是全选还是选一部分？

**答案：选一部分（3~12 个）**

### 选择流程

```
┌─────────────────────────────────────────────────────┐
│ Phase 1: Catalog                                    │
├─────────────────────────────────────────────────────┤
```

### 选择依据

Agent 在 catalog 阶段如何从 35 个文件中选 3~12 个？

```
依据优先级:
1. 文件名含义
   - main.py、core.py、__init__.py > utils.py、helpers.py
   - models.py、views.py、controllers.py > tests_*.py

2. LOC（代码行数）
   - 300 行 > 50 行
   - 大文件通常更核心

3. 目录位置
   - 根目录、核心目录 > 边缘目录
   - src/core/ > src/utils/

4. 文件类型
   - 核心逻辑 > 工具函数 > 测试
   - models.py > utils.py > test_models.py

5. page_brief
   - 根据页面要覆盖的内容要点选择文件
   - "用户认证流程" → login.py、register.py、auth_middleware.py
```

### 实际案例

```
目录: src/auth/（35个文件）

文件清单:
  src/auth/login.py (250 行)
  src/auth/logout.py (80 行)
  src/auth/register.py (300 行)
  src/auth/middleware.py (150 行)
  src/auth/utils.py (100 行)
  src/auth/validators.py (120 行)
  src/auth/models.py (180 行)
  src/auth/api.py (200 行)
  src/auth/config.py (90 行)
  ... (还有 26 个文件)

Agent 选择（认证系统页面）:
  {
    "id": "auth",
    "title": "认证系统",
    "dependent_files": [
      "src/auth/login.py",        ✓ 登录核心
      "src/auth/register.py",     ✓ 注册核心
      "src/auth/middleware.py",   ✓ 认证中间件
      "src/auth/models.py",       ✓ 数据模型
      "src/auth/config.py",       ✓ 配置
      "src/auth/api.py",          ✓ API 接口
      "src/auth/validators.py"    ✓ 验证逻辑
    ],
    "page_brief": "登录流程、注册流程、认证中间件、用户模型、配置项"
  }

结果: 7 个文件（而不是 35 个全选）
```

### 为什么不全选？

```
问题 1: 上下文限制
  - 35 个文件 × 平均 150 行 = 5250 行代码
  - Token 消耗: 约 50k tokens
  - LLM 上下文可能装不下

问题 2: 噪音干扰
  - 工具函数、测试文件不是核心
  - 冗余信息降低文档质量

问题 3: 成本控制
  - 选择代表性文件降低 token 消耗
  - 10-20 倍的 token 差异

解决方案:
  - Agent 在 catalog 阶段选择代表性文件
  - 宁精勿滥，质量优先
```

## 关键设计决策

### 1. 为什么不内置 LLM？

```
优势:
  ✓ Agent 可替换（Claude Code、OpenCode、人工）
  ✓ LLM 可选（Claude、GPT-4、本地模型）
  ✓ 工具丰富（Read、Write、Bash、WebFetch）
  ✓ 多轮反馈（check → fix → check）
  ✓ 并发安全（多 agent 协作）

劣势:
  ✗ 需要安装 Agent
  ✗ 需要理解 Agent 工作流程

结论:
  职责分离，确定性框架 + 智能执行 = 最佳质量
```

### 2. 为什么选择 3~12 个文件？

```
因素 1: 上下文限制
  - 太多文件超出 LLM 上下文
  - 代码文件平均 150 行
  - 12 个文件 × 150 行 = 1800 行 ≈ 18k tokens
  - 在上下文窗口内

因素 2: 质量控制
  - 宁精勿滥
  - 代表性文件更聚焦核心
  - 避免 noise 降低文档质量

因素 3: 成本控制
  - 10-20 倍的 token 差异
  - 12 个文件 vs 35 个文件

结论:
  3~12 个代表质量、成本、上下文的平衡点
```

### 3. 为什么需要确定性校验？

```
LLM 的不确定性:
  - 同一输入，不同输出
  - H1 可能写错
  - 行号可能超出范围
  - 锚点格式可能错误

repowiki 的确定性:
  - H1 必须是任务指定标题
  - 行号自动修正
  - 锚点自动修复
  - 路径必须存在

结论:
  确定性校验 + 自动修复 = 质量保证
```

### 4. 为什么需要并发安全？

```
大仓库场景:
  - 50 个页面任务
  - 串行: 2-4 小时
  - 并发（4 agent）: 30-60 分钟

并发风险:
  - 多个 agent 认领同一任务
  - 数据竞争
  - 死锁

解决方案:
  - 原子认领（mkdir）
  - 心跳续期（touch）
  - 过期回收（stale）
  - 文件锁（.index.lock）

结论:
  原子操作 + 心跳机制 = 并发安全
```

### 5. 为什么需要渐进式渲染？

```
传统流程问题:
  - 必须全部完成才能看到成果
  - 中途失败，看不到部分成果
  - 调试困难

渐进式渲染:
  - 部分完成就能看到部分站点
  - 草稿站点可视化进度
  - 全部完成自动 finalize
  - 调试友好

结论:
  渐进式渲染 = 用户体验提升
```

## 总结

### 核心思想

```
Agent = LLM + Tools + Prompt + Harness
repowiki = 确定性框架 + 质量保证

Agent 负责智能: 读代码、理解、写文档
repowiki 负责确定性: 规划、校验、修复、组装

分离 = 可替换 + 高质量 + 并发安全
```

### 架构优势

1. **零 LLM 依赖**：repowiki 不绑定任何大模型
2. **Agent 可替换**：Claude Code、OpenCode、人工都行
3. **确定性质量**：模板强制 + 程序化校验
4. **并发安全**：原子认领 + 心跳机制
5. **渐进式体验**：部分完成即可查看

### 设计哲学

> **Agent 负责聪明，repowiki 负责靠谱**

- LLM 是"神经元"
- Agent 是"大脑+身体"
- repowiki 是"尺子和模板"
